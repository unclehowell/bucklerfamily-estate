# Contributing — for AI agents

The Academy work board is a **candidate discovery index**, not the claim or status ledger. GitHub Issues are canonical for public-safe project work.

## 1. Find or claim the canonical issue

- Search the Cedwyn repository and relevant linked repositories for an existing issue covering the deliverable.
- Reuse the matching issue; do not create a duplicate. Claim it with a comment recording agent identity/version, UTC timestamp, scope and intended branch. Assign it where appropriate.
- If no suitable issue exists, create one with the **Agent work item** form. The Academy job ID is an optional discovery reference only.
- Do not claim a candidate job in the Academy JSON. A GitHub issue comment and its live lease (where the Hive queue provides one) identify the active writer.

## 2. Work

- Read the live page first. Research public sources. Cite facts to a record (EV-####, MR-####, or a full archive reference).
- Write in the house voice (SOUL.md): short headlines, text blocks clamped at three lines with "read more", provenance as the source only, no page explaining itself, exact title words.
- Make the smallest change that meets the issue's acceptance criteria.
- Keep scope, progress, decisions, dependencies and blockers on the canonical issue. Use the Academy JSON only to discover candidate work.

## 3. Submit

- Open a **pull request** linked to the canonical issue, targeting the branch named by that issue.
- Title: a meaningful summary. Body: the issue relationship, acceptance criteria addressed, exact sources read, tests, preview/live verification and remaining limitations.
- Use a closing reference only when the PR fully satisfies the issue. A partial PR uses "Part of #123" and leaves the issue open.
- The agent lint runs on every pull request. A failing lint is never merged.

## 4. Review and live

An authorised reviewer checks the publish gate, merges when appropriate, waits for the site build and verifies the page live at phone width and desktop. A GitHub issue is completed only after its acceptance criteria and independent verification evidence are recorded. A generated work-board refresh does not close it.

## Private correspondence boundary

HubSpot is restricted to private recipient-facing drafts and exact-version correspondence review. Do not copy email text, recipient identities, contact details, private CRM/task IDs, thread IDs, attachments, personal data, confidential sources or case-specific facts into public issues, comments, branches, pull requests or public feeds. Public issues may carry only a generic, non-identifying engineering/process description where necessary.

## What never to submit

Private people's names or contact details; anything about the family's present holdings or addresses; payment offers; accusations against named people; credentials; confidential correspondence; outbound links where the publish rules prohibit them; insignia designs.
